# btw: project notes

Goal: Baptize 2027 church signup, entirely by SMS through voip.ms, on Vercel serverless functions with Supabase. Churches pick a language and answer ~14 questions one text at a time; the last answer finishes the signup, and the reply thanks them with a link to their own page where they can see and change every answer. Reviewers work in `/admin` ("SMS Gateway"): see signups, text pastors, edit answers. Setup and usage are in `README.md`; the 2026-10-23 build session (what was built, the decisions behind it, what's left, tooling quirks) is in `docs/session-2026-10-23.md`.

Live site: https://baptize.app (Vercel project `btw`; also https://btw-dusky.vercel.app, which voip.ms's callback uses). Database: Supabase project `supabase-cobalt-saddle` (ref `jrkhnieyramucpegntln`), which is **shared with other apps**: everything of ours is prefixed `btw_`, and nothing else in it should be touched.

## Status
- `api/sms-send.js`: sends a text. POST with a Bearer `SMS_SEND_KEY`. `sendText` uses `sendSMS` when the text fits one SMS segment (160 GSM-7 characters, but only 70 once any character needs Unicode, e.g. a language name in its own script), and `sendMMS` for anything longer (up to 2048) or media (up to 3 URLs). The first live reply failed with `sms_toolong` because the menu (all 10 languages on, native-script labels) was 136 Unicode characters sent as SMS.
- `api/sms-inbound.js`: the voip.ms SMS URL callback. Texts from short codes and other non-10-digit senders (e.g. WhatsApp's 29283) are never answered but show in the Log panel (`info`, source `short-code`, with the text). Checks `?key=SMS_INBOUND_KEY`, accepts GET (with `&` or `;` between values) or POST JSON, normalizes the message to `{id, from, to, message, date, media}` and runs the conversation: any text to the number starts or continues that number's signup (no keyword). A new number's first text goes to Google's language detection (`detect()` in `lib/translate.js`): when it has 4+ letters, confidence is 0.8+ and the language is switched on, the signup starts in that language (`engine.startIn`: `lang_detected`, `welcome`, first question); otherwise, or if detection fails (logged as a warning), it gets the menu. STOP as a first text still opts out. MENU (`kw_menu`, built in) brings the menu back at any point; picking a language then keeps the answers and resumes where they were. It records the text in `btw_messages` (a repeated voip.ms `id` is a retry and is ignored), loads `btw_sessions` + `btw_churches` for the phone (`+1XXXXXXXXXX`), runs `engine.reply`, saves both rows, then sends the replies through `sendText`. Answers live only in `btw_churches`; the session row holds phase, lang, queue, editing. `status` is `complete` from the first DONE until a restart, `opted_out` after STOP. A failed send is logged and not retried, since the state is already saved. Failures go to `btw_events` (see Log panel) and a reply that wasn't sent is kept in `btw_messages` with its `error`. Receiving confirmed live on 2026-10-23; the first reply failed (`sms_toolong`, fixed since).
- Prompt editor (`/admin`, `api/admin/*`): done, and working live against the real Supabase and Google Translate (login, loading prompts, Google drafts all confirmed in production). The user edits in English only: once an English prompt is saved and newer than a translation (by `updated_at`), it shows Translate, which calls `api/admin/translate-all` to translate and **save** into every language that is on or started, then shows the results in a dialog. While viewing another language, each prompt's English box has **Edit English**: edit in place (same 160 cap) and **Save and translate** saves the English and runs `translate-all`, so a translation that runs long is fixed by shortening the English without switching languages.
- Conversations panel (`/admin`, `api/admin/conversations.js`): lists every `btw_churches` row (newest activity first, status tabs, search) with where the person is from `btw_sessions`; clicking one opens its `btw_messages` thread as chat bubbles beside the saved answers. Refresh buttons (no auto-refresh), and a Delete button in the thread (`DELETE /api/admin/conversations?phone=`) that removes the number's session, answers, texts and logged problems so its next text starts fresh (useful for testing; deletes through the Supabase MCP tool time out). Unsent replies show dashed in red with the reason.
- Team messages (migration `20261023180000`: `btw_messages.thread` 'signup' | 'team', `read_at`, `translation`): in a conversation's **Messages** tab a reviewer texts the pastor from the signup number (`POST /api/admin/conversations?phone=` `{ body }`; refused after STOP; `{ translate }` drafts the English into the pastor's signup language to check before sending). Once a signup has been completed (`completed_at`, even while an answer is being edited since), any text that isn't a command (the English translation is skipped when it only differs in curly vs straight quotes) (the engine flags its fallback reply as `unhandled`) goes to the team thread unread, with Google's English translation, and also gets `info_reply` (what they can text: photos, a baptism count) at most once a day (migration `20261024050000`); a number is instead their baptism count (`readCount` in `lib/counts.js`: a number alone in any script's digits, a number word in en/es/pt/fr such as "nove" or "treinta y cinco", or one number with a baptism word in any of the 10 languages such as "14 bautismos" or "今天14人受洗"; two numbers, like "14 at 10am", aren't a count) (`btw_churches.baptisms`, `baptisms_at`; the latest wins; reply `count_saved`; shown in /admin's answers panel and Churches screen). One over 1,000, or more than ten times (and 20 above) the last, waits in `baptisms_pending` / `baptisms_pending_at` for a YES within a day (`count_confirm`; NO: `count_not_saved`), checked before the photo YES/NO. Baptisms mentioned without a single number go to the team and get `count_ask` (migration `20261025090000`). Mid-signup, replies still go to the bot, so a reviewer who wants to talk presses **Finish signup** (tab row of the conversation, shown while a signup is unfinished; `POST /api/admin/conversations?phone=` `{ finish: true }`): it sets the session to `done` and the church to complete (with a page key), texts nothing, and from then on their free text goes to the team thread; missing answers stay blank for Edit answers, and EDIT <n> still works. ## Decisions (the user's; details in docs/session-2026-10-23.md)
- Any text starts or continues a signup; no keyword.
- No numbered summary to confirm: the last answer finishes the signup, and changes are made on the pastor's page (link in the thank-you). Churches outside the US are accepted (country question; free-form region and postal code).
- One church per phone number. Multi-church was proposed and declined. RESTART after a finished signup no longer wipes it (2026-10-25).
- Every prompt at most 160 characters. Long translations are fixed by shortening the English and translating again.
- All 14 signup questions stay by text; on 2026-10-25 the 12 longest prompts (`welcome`, `web_form_link`, `lang_detected`, `ask_church`, `ask_country`, `ask_denom`, `ask_website`, `ask_contact`, `ask_baptism`, `ask_b_street`, `ask_map`, `ask_consent`, which now starts "Last one:") were shortened by hand in all 10 languages (migration `20261025120000`), keeping each language's keywords. Moving questions to the church's page was offered and declined.
- Reviewers share the signup number. A finished signup's free text goes to the team thread; there's no open/close chat switch. Alerts: unread badges, plus opt-in text alerts per team member (2026-10-25).
- All users have equal rights. Editing answers never changes the texts.
- Simulations live in the real database, flagged and badged, and are never texted.
- The public map exists elsewhere; this app only stores `public_map`.
- Workflow: work on `claude/intelligent-brown-8znoxb` reset onto `main`, then a PR, merged only when the user says so. Migrations are applied through the Supabase MCP and also saved under `supabase/migrations/`.

## Tooling quirks
- Supabase returns at most 1000 rows per request. `btw_prompts` (one row per prompt per language) passed that with the country change (1053 rows) and was 1203 on 2026-10-24, so the newest prompts silently went missing (a texted photo's permission question went out empty: voip.ms `message_empty`). Whole-table reads use `dbAll()` in `lib/supabase.js` (pages with `limit`/`offset`; give it an `order`), and an empty reply is logged instead of sent.
- `btw_web_requests.kind` has a check constraint listing every kind `record()` uses; a new kind needs it updated (migration `20261025150000`), or the insert fails with a 500. `dev/fake-db.mjs` doesn't enforce constraints, so tests won't catch it: the 30-days resend and the parent link text both broke live this way on 2026-10-25.
- Supabase MCP: reads and `apply_migration` work; DELETE via `execute_sql` times out (use `/admin`'s Delete button).
- Vercel MCP: deployments and runtime logs work (project `prj_0mYe7r3u736ewePhPOnodWuQQSQ7`, team `team_lgFLmF4DFBT7H0DS0A1KcLNr`); listing env vars is forbidden.
- The live site isn't reachable from the sandbox; test with `dev/server.mjs` and Playwright (`/opt/pw-browsers/chromium`).

## Open questions (verify against https://voip.ms/m/apidocs.php)
1. ~~Format of the incoming callback~~: answered live. voip.ms sends GET with the placeholders filled in and `&` between them, e.g. `{"id":"113367333","from":"9498709493","to":"7147165116","message":"Hi 2","date":"2026-10-23 11:37:00"}` once normalized (`date` is local time, no zone). `flattenBody` / `parseQuery` could be simplified to match. One request took about 7 seconds end to end (incl. a relay send).
2. Does `rest.php` accept POST for `sendSMS`, or only GET? The code POSTs form-encoded data for both.
3. The response field holding the message id: `sms` for `sendSMS`, `mms` for `sendMMS`? The code assumes so.
4. Does `sendMMS` accept media URLs in `media1..3`, or only base64? (Needed before reviewers can send pictures.)
6. How long do the `{MEDIA}` links stay up, and do they need a login? Check with a real MMS: if the thumbnail in /admin doesn't load, the links aren't public.
5. ~~Placeholder names~~: `{TO}`, `{FROM}`, `{MESSAGE}`, `{ID}`, `{TIMESTAMP}` all fill in.
