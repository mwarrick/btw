# btw: project notes

Goal: Baptize 2027 church signup, entirely by SMS through voip.ms, on Vercel serverless functions with Supabase. Churches pick a language and answer ~14 questions one text at a time; the last answer finishes the signup, and the reply thanks them with a link to their own page where they can see and change every answer. Reviewers work in `/admin` ("SMS Gateway"): see signups, text pastors, edit answers. Setup and usage are in `README.md`; the 2026-10-23 build session (what was built, the decisions behind it, what's left, tooling quirks) is in `docs/session-2026-10-23.md`.

Live site: https://btw-dusky.vercel.app (Vercel project `btw`). Database: Supabase project `supabase-cobalt-saddle` (ref `jrkhnieyramucpegntln`), which is **shared with other apps**: everything of ours is prefixed `btw_`, and nothing else in it should be touched.

## Layout
- `public/`: the only folder Vercel publishes (`vercel.json` sets `outputDirectory`). Before that, the whole repo, `docs/` and `CLAUDE.md` included, was publicly downloadable. `cleanUrls` serves `admin.html` at `/admin`.
  - `index.html`: browser demo. Runs `js/engine.js` on the live prompts from `GET /api/prompts`, so edits at `/admin` show there (that endpoint is cached 15s at Vercel's edge).
  - `admin.html`: the "SMS Gateway" admin (vanilla JS module, no build step). A tab bar switches screens by `data-screen` on each section, kept in the URL hash: `#conversations` (default; unread count on the tab; each row has a Message button that opens the conversation on its Messages tab), `#churches` (every signup with `completed_at`, newest first, with contact details, address, search, and Edit / Conversations / Message buttons; built from the same `GET /api/admin/conversations` list, which now includes those fields), `#prompts`, `#languages` (on/off, menu labels, first-message preview), `#log`, `#users`, `#connection` (voip.ms checks and test text). The setup login sees only Users, with no tab bar.
  - `js/engine.js`: the conversation as a pure function, `reply(state, text) -> { state, replies }`. Shared by the demo and the SMS handler. State is JSON for `btw_sessions`; `data` uses `btw_churches` column names. The first message is `menu_intro`, then `<n> <menu_label>` per switched-on language, then `menu_footer`. After an opt-out (STOP and the other carrier words) it sends nothing until START.
  - `js/sms.js`: GSM-7 / Unicode segment counting, imported by the pages and by the API.
- `api/`: serverless functions. `api/admin/*` needs a logged-in user (`await requireAdmin(req, res)` returns the user or answers 401).
- `lib/`: server helpers. `voipms.js` (voip.ms API calls and `sendText`, direct or via the relay), `supabase.js` (PostgREST over fetch), `events.js` (`logEvent()` into `btw_events` for the Log panel; never throws), `admin-auth.js` (users in `btw_users`, scrypt passwords, HMAC cookie `id.session_version.exp.sig` keyed by `ADMIN_PASSWORD`, checked against the database on every request), `prompts.js` (English-only keys, quote straightening, placeholder checks, `loadPrompts()` for the engine), `translate.js` (Google v2 behind `translate()` and `detect()`).
- `supabase/migrations/`: schema and seed, already applied to the shared project.
- `dev/`: local testing, not deployed. `node dev/server.mjs` serves `public/` and every API handler on http://localhost:8787 against `dev/fake-db.mjs` (in-memory Supabase, fake voip.ms and Google Translate); setup password `pw`.
- No package.json and no dependencies; everything relies on Node's built-in `fetch`.

## Status
- `api/sms-send.js`: sends a text. POST with a Bearer `SMS_SEND_KEY`. `sendText` uses `sendSMS` when the text fits one SMS segment (160 GSM-7 characters, but only 70 once any character needs Unicode, e.g. a language name in its own script), and `sendMMS` for anything longer (up to 2048) or media (up to 3 URLs). The first live reply failed with `sms_toolong` because the menu (all 10 languages on, native-script labels) was 136 Unicode characters sent as SMS.
- `api/sms-inbound.js`: the voip.ms SMS URL callback. Checks `?key=SMS_INBOUND_KEY`, accepts GET (with `&` or `;` between values) or POST JSON, normalizes the message to `{id, from, to, message, date, media}` and runs the conversation: any text to the number starts or continues that number's signup (no keyword). A new number's first text goes to Google's language detection (`detect()` in `lib/translate.js`): when it has 4+ letters, confidence is 0.8+ and the language is switched on, the signup starts in that language (`engine.startIn`: `lang_detected`, `welcome`, first question); otherwise, or if detection fails (logged as a warning), it gets the menu. STOP as a first text still opts out. MENU (`kw_menu`, built in) brings the menu back at any point; picking a language then keeps the answers and resumes where they were. It records the text in `btw_messages` (a repeated voip.ms `id` is a retry and is ignored), loads `btw_sessions` + `btw_churches` for the phone (`+1XXXXXXXXXX`), runs `engine.reply`, saves both rows, then sends the replies through `sendText`. Answers live only in `btw_churches`; the session row holds phase, lang, queue, editing. `status` is `complete` from the first DONE until a restart, `opted_out` after STOP. A failed send is logged and not retried, since the state is already saved. Failures go to `btw_events` (see Log panel) and a reply that wasn't sent is kept in `btw_messages` with its `error`. Receiving confirmed live on 2026-10-23; the first reply failed (`sms_toolong`, fixed since).
- Prompt editor (`/admin`, `api/admin/*`): done, and working live against the real Supabase and Google Translate (login, loading prompts, Google drafts all confirmed in production). The user edits in English only: once an English prompt is saved and newer than a translation (by `updated_at`), it shows Translate, which calls `api/admin/translate-all` to translate and **save** into every language that is on or started, then shows the results in a dialog. While viewing another language, each prompt's English box has **Edit English**: edit in place (same 160 cap) and **Save and translate** saves the English and runs `translate-all`, so a translation that runs long is fixed by shortening the English without switching languages.
- Conversations panel (`/admin`, `api/admin/conversations.js`): lists every `btw_churches` row (newest activity first, status tabs, search) with where the person is from `btw_sessions`; clicking one opens its `btw_messages` thread as chat bubbles beside the saved answers. Refresh buttons (no auto-refresh), and a Delete button in the thread (`DELETE /api/admin/conversations?phone=`) that removes the number's session, answers, texts and logged problems so its next text starts fresh (useful for testing; deletes through the Supabase MCP tool time out). Unsent replies show dashed in red with the reason.
- Team messages (migration `20261023180000`: `btw_messages.thread` 'signup' | 'team', `read_at`, `translation`): in a conversation's **Messages** tab a reviewer texts the pastor from the signup number (`POST /api/admin/conversations?phone=` `{ body }`; refused after STOP; `{ translate }` drafts the English into the pastor's signup language to check before sending). Once a signup has been completed (`completed_at`, even while an answer is being edited since), any text that isn't a command (the English translation is skipped when it only differs in curly vs straight quotes) (the engine flags its fallback reply as `unhandled`) goes to the team thread unread, with Google's English translation, and gets no bot reply; EDIT/STOP/HELP/MENU/RESTART still go to the bot. Mid-signup, replies still go to the bot, so a reviewer who wants to talk presses **Finish signup** (tab row of the conversation, shown while a signup is unfinished; `POST /api/admin/conversations?phone=` `{ finish: true }`): it sets the session to `done` and the church to complete (with a page key), texts nothing, and from then on their free text goes to the team thread; missing answers stay blank for Edit answers, and EDIT <n> still works. The dialog's title and Signup/Messages tabs stay pinned while the thread scrolls. Unread counts show on the list (Unread tab, "n new" chip) and opening the conversation marks them read. No email/text alert to reviewers yet.
- Users (migration `20261023190000`, `api/admin/users.js`, Users section in `/admin`): one login per person (email + password, min 8), all with equal rights: add, rename, set a new password, remove (soft: `active = false`, so their messages keep their name; you can't remove yourself). A password change or removal bumps `session_version`, signing that person out everywhere (your own change re-issues your cookie). Team messages record `btw_messages.sent_by` and show "Sent by <name>". While no user exists, `ADMIN_PASSWORD` logs in as "Setup", which can only add users (other endpoints answer 403); once one exists it no longer logs in, but it still signs the cookies, so changing it signs everyone out.
- Editing answers (migration `20261023200000`: `btw_churches.edited_by`, `edited_at`; `api/admin/churches.js` GET/PATCH `?phone=`): Edit on the Churches screen or Edit answers in a conversation opens a form over every `btw_churches` answer, checked like the SMS signup (email, US state by name or code, 5-digit ZIP, 10-digit phone, website). Only the saved answers change; `btw_messages` is never touched. "Edited <date> by <name>" shows on the Churches row and in the answers panel. A pastor's later `EDIT <n>` by text starts from the edited values.
- Simulations (migration `20261023210000`: `btw_churches.simulated`; `lib/simulations.js`, `api/admin/simulations.js` POST add / DELETE remove; panel at the bottom of Conversations): eleven scripted pastors run through the real engine with the live prompts (bot replies are exactly what a pastor would get), then reviewer/pastor follow-ups in the Messages thread and the answer edits they led to. Covers English/Spanish/Chinese, a church in Canada, detection and the menu, input mistakes, EDIT, MENU switching, STOP, an abandoned signup and an unread question. Fictional 555-01xx numbers, "Simulation" badge everywhere; a message sent to a simulated number is saved but never texted. Adding replaces earlier simulations; scenarios in a language that's switched off are skipped. Reviewer messages and edits are credited to whoever pressed Add.
- Country and no summary (migration `20261024000000`): after the church's name the engine asks `ask_country` ("Is your church in the US? Reply YES, or send the name of your country."). YES or a typed US name (USA, U.S., Estados Unidos, 美国, ...; `countryValue()` in `engine.js`) stores `country = 'US'`; anything else is kept as typed (lowercase Latin capitalized). Outside the US, the state and ZIP questions (church and baptism site, which shares the church's country) become `ask_region` / `ask_postal`: any region, and a postal code of letters, digits, spaces and dashes up to 10 (`err_postal`), both SKIPpable. `lib/church-fields.js` checks the same way for `/admin` and the pastor's page. Rows from before have `country` 'US' (backfilled where a state was given) or null, which counts as US. The numbered summary is no longer sent: the last answer (consent) sets phase `done` (so `completed_at`) and replies `done` + `done_link`; an `EDIT <n>` by text still works with the old numbers (country is 13) and ends with `edit_saved` + the link; DONE re-sends the link. `done`, `done_reply` and `help` were reworded in all 10 languages to drop EDIT/summary; wrong machine-translated labels (`sum_zip` as "zipper" in es/fr/zh/ar, `sum_state` as "status" in ru/zh) were fixed.
- Chinese keywords need fixing (found while scripting the simulations): `kw_done` is 完毕 but `sum_outro` tells people to reply 完成, `kw_no` is 非 (should include 不 / 否), and `kw_yes` (是的，Y) lacks plain 是. English words always work as a fallback.
- Pastor's page (migration `20261023220000`: `btw_churches.profile_key`, prompts `done_link` + `web_*` hand-translated into all 10 languages; `lib/profile-link.js`, `api/profile.js`, `public/profile.html`, rewrite `/p/:key` → `/profile` in `vercel.json` (not `/profile.html`: with `cleanUrls` that 404s)): the finishing message ends with `done_link`, "See or update your signup anytime: https://btw-dusky.vercel.app/p/<key>" (88 characters in English; with the English `done` it's 141, one SMS). The key is 128 random bits (22 characters), made when the signup first finishes and kept, so the link never changes; signups finished before this got 32-hex keys from the migration. The link is the only login: it opens that one signup. The phone shows read-only under the email (`web_phone`, `web_phone_hint`, migration `20261023230000`); it's sent apart from the answers and never saved from the page. The page is one ~9 KB file (inline CSS/JS, system font, no images, one API call), mobile-first, in the signup's language (labels and errors reuse `sum_*`, `val_*`, `err_*`; RTL for ar/ur), and checks answers with the same rules as `/admin` (`lib/church-fields.js`). A pastor's save sets `edited_at` with `edited_by` empty, shown in `/admin` as "Edited … by the pastor"; the conversation's answers panel shows the link (Pastor's page, opens in a new tab, as does the website) so a reviewer can resend it. Links don't expire and can't be revoked from `/admin` yet. **Send login link** (Messages tab, next to Send; `POST /api/admin/conversations?phone=` `{ sendLink: true }`) texts the pastor `done_link` with their link in their language as a team message from the reviewer, making the key first if the signup has none (e.g. signups finished before links existed, or unfinished ones); refused after STOP, saved but not texted for simulations. `PUBLIC_SITE_URL` (optional) sets the link's address; otherwise the request's host is used.
- The 10 simulations are loaded in the live database (added from the live site on 2026-10-23); since the country change there are 11 (a Canadian church added), and re-adding them replaces the old ones.
- Log panel (`/admin`, `api/admin/events.js`): the latest 200 `btw_events` rows (errors and warnings from `sms-inbound` and `sms-send`), with a link from a phone number to its conversation. Checked in a browser against an in-memory database, not yet against production.
- Each prompt is capped at 160 characters (`PROMPT_MAX` in `lib/prompts.js`, mirrored in `admin.html`): the box stops typing there, `PUT /api/admin/prompts` refuses longer text, and `translate-all` doesn't save a translation that runs over. As of 2026-10-23, 20 saved translations (none in English) were over the cap; the editor flags them as "too long" and lists them under "Only what needs work" (all fixed since: 0 over the cap at the end of 2026-10-23). Messages built from several prompts (menu, summary) can still run longer and go out as MMS.
- `lang_detected` and `kw_menu` (migration `20261023170000`) were translated by hand into all 10 languages; worth a native-speaker check.
- Prompt text is data: 99 keys in `btw_prompt_keys`, text per language in `btw_prompts`. Field order, validation and branching stay in code. Keys `menu_intro`, `menu_footer` and `menu_invalid` are English only (sent before a language is picked). All 10 languages were switched on as of 2026-10-23.

## Decisions (the user's; details in docs/session-2026-10-23.md)
- Any text starts or continues a signup; no keyword.
- No numbered summary to confirm: the last answer finishes the signup, and changes are made on the pastor's page (link in the thank-you). Churches outside the US are accepted (country question; free-form region and postal code).
- One church per phone number. Multi-church was proposed and declined. Known risk: RESTART after DONE wipes that phone's answers.
- Every prompt at most 160 characters. Long translations are fixed by shortening the English and translating again.
- Reviewers share the signup number. A finished signup's free text goes to the team thread; there's no open/close chat switch. Alerts: unread badges only.
- All users have equal rights. Editing answers never changes the texts.
- Simulations live in the real database, flagged and badged, and are never texted.
- The public map exists elsewhere; this app only stores `public_map`.
- Workflow: work on `claude/intelligent-brown-8znoxb` reset onto `main`, then a PR, merged only when the user says so. Migrations are applied through the Supabase MCP and also saved under `supabase/migrations/`.

## Open questions (verify against https://voip.ms/m/apidocs.php)
1. ~~Format of the incoming callback~~: answered live. voip.ms sends GET with the placeholders filled in and `&` between them, e.g. `{"id":"113367333","from":"9498709493","to":"7147165116","message":"Hi 2","date":"2026-10-23 11:37:00"}` once normalized (`date` is local time, no zone). `flattenBody` / `parseQuery` could be simplified to match. One request took about 7 seconds end to end (incl. a relay send).
2. Does `rest.php` accept POST for `sendSMS`, or only GET? The code POSTs form-encoded data for both.
3. The response field holding the message id: `sms` for `sendSMS`, `mms` for `sendMMS`? The code assumes so.
4. Does `sendMMS` accept media URLs in `media1..3`, or only base64?
5. ~~Placeholder names~~: `{TO}`, `{FROM}`, `{MESSAGE}`, `{ID}`, `{TIMESTAMP}` all fill in.
