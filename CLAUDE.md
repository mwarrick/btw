# btw: project notes

Goal: Baptize 2027 church signup, entirely by SMS through voip.ms, on Vercel serverless functions with Supabase. Churches pick a language and answer ~14 questions one text at a time; the last answer finishes the signup, and the reply thanks them with a link to their own page where they can see and change every answer. Reviewers work in `/admin` ("SMS Gateway"): see signups, text pastors, edit answers. Setup and usage are in `README.md`; the 2026-10-23 build session (what was built, the decisions behind it, what's left, tooling quirks) is in `docs/session-2026-10-23.md`.

Live site: https://btw-dusky.vercel.app (Vercel project `btw`). Database: Supabase project `supabase-cobalt-saddle` (ref `jrkhnieyramucpegntln`), which is **shared with other apps**: everything of ours is prefixed `btw_`, and nothing else in it should be touched.

## Layout
- `public/`: the only folder Vercel publishes (`vercel.json` sets `outputDirectory`). Before that, the whole repo, `docs/` and `CLAUDE.md` included, was publicly downloadable. `cleanUrls` serves `admin.html` at `/admin`.
  - `index.html` (`/`): the front page, three ways in, in the browser's language (picker; wording `land_*`, migration `20261024120000`, from `GET /api/profile?part=landing`). **Church organizers**: Sign up your church (`/signup?lang=`), "Or text {number}" (the `VOIPMS_DID`, as an `sms:` link) and **Get my link** (`POST /api/profile?part=link` `{ phone }`: a signed-up, not opted-out, not simulated number is texted `login_link`, at most once per 10 minutes, logged as an `info` event from `get-link`; the answer is the same either way, so it doesn't reveal who signed up). **I was baptized**: Coming soon (`docs/plan-testimonies.md`). **Team**: `/admin`.
  - `profile.html` at `/signup` (rewrite in `vercel.json`): the web signup form. Without a key the pastor's page becomes a signup form (phone editable, language picker, `?lang=` from the front page, consent box); `POST /api/profile` saves a finished signup (`completed_at`, `consent_at`, `profile_key`) and a `done` session, so later texts from that phone are handled as finished, then opens `/p/<key>?welcome=1`. Nothing is texted. Refused (409) when the phone already has a signup. Prompts `web_signup_*` etc. (migration `20261024110000`). Not verified: see `docs/gaps.md`.
  - `demo.html` (`/demo`): browser demo. Runs `js/engine.js` on the live prompts from `GET /api/prompts`, so edits at `/admin` show there (that endpoint is cached 15s at Vercel's edge).
  - `admin.html`: the "SMS Gateway" admin (vanilla JS module, no build step). A tab bar switches screens by `data-screen` on each section, kept in the URL hash: `#conversations` (default; unread count on the tab; each row has a Message button that opens the conversation on its Messages tab), `#churches` (every signup with `completed_at`, newest first, with contact details, address, search, and Edit / Conversations / Message buttons; built from the same `GET /api/admin/conversations` list, which now includes those fields), `#prompts`, `#languages` (on/off, menu labels, first-message preview), `#log`, `#users`, `#connection` (voip.ms checks and test text). The setup login sees only Users, with no tab bar.
  - `js/engine.js`: the conversation as a pure function, `reply(state, text) -> { state, replies }`. Shared by the demo and the SMS handler. State is JSON for `btw_sessions`; `data` uses `btw_churches` column names. The first message is `menu_intro`, then `<n> <menu_label>` per switched-on language, then `menu_footer`. After an opt-out (STOP and the other carrier words) it sends nothing until START.
  - `js/sms.js`: GSM-7 / Unicode segment counting, imported by the pages and by the API.
- `api/`: serverless functions. `api/admin/*` needs a logged-in user (`await requireAdmin(req, res)` returns the user or answers 401).
- `lib/`: server helpers. `voipms.js` (voip.ms API calls and `sendText`, direct or via the relay), `supabase.js` (PostgREST over fetch), `events.js` (`logEvent()` into `btw_events` for the Log panel; never throws), `admin-auth.js` (users in `btw_users`, scrypt passwords, HMAC cookie `id.session_version.exp.sig` keyed by `ADMIN_PASSWORD`, checked against the database on every request), `prompts.js` (English-only keys, quote straightening, placeholder checks, `loadPrompts()` for the engine), `translate.js` (Google v2 behind `translate()` and `detect()`).
- `supabase/migrations/`: schema and seed, already applied to the shared project.
- `dev/`: local testing, not deployed. `node dev/server.mjs` serves `public/` and every API handler on http://localhost:8787 against `dev/fake-db.mjs` (in-memory Supabase, fake voip.ms and Google Translate); setup password `pw`.
- No package.json and no dependencies; everything relies on Node's built-in `fetch`.

## Status
- `api/sms-send.js`: sends a text. POST with a Bearer `SMS_SEND_KEY`. `sendText` uses `sendSMS` when the text fits one SMS segment (160 GSM-7 characters, but only 70 once any character needs Unicode, e.g. a language name in its own script), and `sendMMS` for anything longer (up to 2048) or media (up to 3 URLs). The first live reply failed with `sms_toolong` because the menu (all 10 languages on, native-script labels) was 136 Unicode characters sent as SMS.
- `api/sms-inbound.js`: the voip.ms SMS URL callback. Checks `?key=SMS_INBOUND_KEY`, accepts GET (with `&` or `;` between values) or POST JSON, normalizes the message to `{id, from, to, message, date, media}` and runs the conversation: any text to the number starts or continues that number's signup (no keyword). A new number's first text goes to Google's language detection (`detect()` in `lib/translate.js`): when it has 4+ letters, confidence is 0.8+ and the language is switched on, the signup starts in that language (`engine.startIn`: `lang_detected`, `welcome`, first question); otherwise, or if detection fails (logged as a warning), it gets the menu. STOP as a first text still opts out. MENU (`kw_menu`, built in) brings the menu back at any point; picking a language then keeps the answers and resumes where they were. It records the text in `btw_messages` (a repeated voip.ms `id` is a retry and is ignored), loads `btw_sessions` + `btw_churches` for the phone (`+1XXXXXXXXXX`), runs `engine.reply`, saves both rows, then sends the replies through `sendText`. Answers live only in `btw_churches`; the session row holds phase, lang, queue, editing. `status` is `complete` from the first DONE until a restart, `opted_out` after STOP. A failed send is logged and not retried, since the state is already saved. Failures go to `btw_events` (see Log panel) and a reply that wasn't sent is kept in `btw_messages` with its `error`. Receiving confirmed live on 2026-10-23; the first reply failed (`sms_toolong`, fixed since).
- Prompt editor (`/admin`, `api/admin/*`): done, and working live against the real Supabase and Google Translate (login, loading prompts, Google drafts all confirmed in production). The user edits in English only: once an English prompt is saved and newer than a translation (by `updated_at`), it shows Translate, which calls `api/admin/translate-all` to translate and **save** into every language that is on or started, then shows the results in a dialog. While viewing another language, each prompt's English box has **Edit English**: edit in place (same 160 cap) and **Save and translate** saves the English and runs `translate-all`, so a translation that runs long is fixed by shortening the English without switching languages.
- Conversations panel (`/admin`, `api/admin/conversations.js`): lists every `btw_churches` row (newest activity first, status tabs, search) with where the person is from `btw_sessions`; clicking one opens its `btw_messages` thread as chat bubbles beside the saved answers. Refresh buttons (no auto-refresh), and a Delete button in the thread (`DELETE /api/admin/conversations?phone=`) that removes the number's session, answers, texts and logged problems so its next text starts fresh (useful for testing; deletes through the Supabase MCP tool time out). Unsent replies show dashed in red with the reason.
- Team messages (migration `20261023180000`: `btw_messages.thread` 'signup' | 'team', `read_at`, `translation`): in a conversation's **Messages** tab a reviewer texts the pastor from the signup number (`POST /api/admin/conversations?phone=` `{ body }`; refused after STOP; `{ translate }` drafts the English into the pastor's signup language to check before sending). Once a signup has been completed (`completed_at`, even while an answer is being edited since), any text that isn't a command (the English translation is skipped when it only differs in curly vs straight quotes) (the engine flags its fallback reply as `unhandled`) goes to the team thread unread, with Google's English translation, and also gets `info_reply` (what they can text: photos, a baptism count) at most once a day (migration `20261024050000`); a text that's only a number (any script's digits) is instead their baptism count (`btw_churches.baptisms`, `baptisms_at`; the latest wins; reply `count_saved`; shown in /admin's answers panel and Churches screen); EDIT/STOP/HELP/MENU/RESTART still go to the bot. Mid-signup, replies still go to the bot, so a reviewer who wants to talk presses **Finish signup** (tab row of the conversation, shown while a signup is unfinished; `POST /api/admin/conversations?phone=` `{ finish: true }`): it sets the session to `done` and the church to complete (with a page key), texts nothing, and from then on their free text goes to the team thread; missing answers stay blank for Edit answers, and EDIT <n> still works. The dialog's title and Signup/Messages tabs stay pinned while the thread scrolls. Unread counts show on the list (Unread tab, "n new" chip) and opening the conversation marks them read. No email/text alert to reviewers yet.
- Users (migration `20261023190000`, `api/admin/users.js`, Users section in `/admin`): one login per person (email + password, min 8), all with equal rights: add, rename, set a new password, remove (soft: `active = false`, so their messages keep their name; you can't remove yourself). A password change or removal bumps `session_version`, signing that person out everywhere (your own change re-issues your cookie). Team messages record `btw_messages.sent_by` and show "Sent by <name>". While no user exists, `ADMIN_PASSWORD` logs in as "Setup", which can only add users (other endpoints answer 403); once one exists it no longer logs in, but it still signs the cookies, so changing it signs everyone out.
- Editing answers (migration `20261023200000`: `btw_churches.edited_by`, `edited_at`; `api/admin/churches.js` GET/PATCH `?phone=`): Edit on the Churches screen or Edit answers in a conversation opens a form over every `btw_churches` answer, checked like the SMS signup (email, US state by name or code, 5-digit ZIP, 10-digit phone, website). Only the saved answers change; `btw_messages` is never touched. "Edited <date> by <name>" shows on the Churches row and in the answers panel. A pastor's later `EDIT <n>` by text starts from the edited values.
- Simulations (migration `20261023210000`: `btw_churches.simulated`; `lib/simulations.js`, `api/admin/simulations.js` POST add / DELETE remove; panel at the bottom of Conversations): eleven scripted pastors run through the real engine with the live prompts (bot replies are exactly what a pastor would get), then reviewer/pastor follow-ups in the Messages thread and the answer edits they led to; finished ones get a random baptism count (5 to 50). Covers English/Spanish/Chinese, a church in Canada, detection and the menu, input mistakes, EDIT, MENU switching, STOP, an abandoned signup and an unread question. Fictional 555-01xx numbers, "Simulation" badge everywhere; a message sent to a simulated number is saved but never texted. Adding replaces earlier simulations; scenarios in a language that's switched off are skipped. Reviewer messages and edits are credited to whoever pressed Add.
- Photos (migration `20261024030000`: private Storage bucket `btw-photos` (another app owns `photos`), table `btw_photos`, prompts `web_tab_*`, `web_photos_intro`, `web_consent`, `web_add_photos`, `web_consent_needed`, `web_uploading`, `web_uploaded`, `web_upload_failed`, `web_delete`, `web_delete_confirm`, `web_no_photos` hand-translated into all 10 languages): the pastor's page has two tabs, Your signup and Photos (`/p/<key>#photos` opens Photos). They tick the permission box (photos may be shared publicly, incl. social media; a parent agrees for anyone under 18) and add photos; the browser shrinks each to 2048 px plus a 480 px thumbnail, re-encoded as JPEG (drops location data), and uploads one at a time as base64 JSON to `api/profile-photos.js` (Vercel's 4.5 MB body limit; files over 3 MB are refused). The exact `web_consent` text in their language is saved with each photo (`consent_text`, `consent_at`). Removing deletes the files and row for good (decided). `lib/storage.js` is Storage over fetch (upload, signed links, delete); `lib/photos.js` lists (signed links, 1 hour), saves and deletes. /admin: a Photos screen (all churches, newest first, "New" count on its tab until opened in the conversation) and a Photos tab in each conversation, both with Delete; deleting a conversation or the simulations deletes their photos too. Texted photos: see MMS in. Resources (migration `20261024060000`): a third tab on the pastor's page (`#resources`) with a button to the organizer's Dropbox folder, the same for every church; the link is the English-only prompt `resources_url` (editable on the Prompts screen; the tab hides without an http(s) link). Photo permission is the church's one choice (migration `20261024070000`: `btw_churches.photos_allowed` true/false/null, `photos_allowed_at`, `photos_consent_text`), not a per-upload checkbox: the Photos tab shows one button, **Opt in** (with the `web_consent` statement) until they allow it, then **Opt out** (with `web_opted_in`; asks `web_opt_out_confirm` first). `PATCH /api/profile-photos` `{ allow }` and a YES/NO to the texted `photo_ask` both call `setPhotoChoice` (lib/photos.js), which applies the choice to all their photos; new photos (uploaded or texted) follow it via `churchChoice`; `photo_ask` is only sent while the choice is null. Photos show `web_waiting_label` (no choice yet) or `web_not_shared_label` (opted out). `web_consent_needed`, `web_photos_waiting` and `web_allow_sharing` are no longer used.
- MMS in (migration `20261024010000`: `btw_messages.media text[]`): the callback URL ends with `&media={MEDIA}` (voip.ms fills in comma-separated attachment links; `parseQuery` takes everything after `media=` whole, since a link may contain `&`). Links are saved with the message (http(s) only, up to 10). voip.ms's own links (`https://voip.ms/media/<token>/media.jpeg`) download fine server-side but don't display in a browser, so a conversation shows our stored copies (`photos` on each message from `GET /api/admin/conversations?phone=`, signed links) as thumbnails that open full size; only a text with no stored copy falls back to its links ("Attachment n" when they don't load). A picture with no words while a question is open (signing up or changing an answer) gets `engine.again()`, the question repeated, instead of an error; after the signup is finished it goes to the team thread unread (no translation). Pictures with words: the words are the answer, the picture is kept. Each picture is also copied into `btw-photos` (migration `20261024040000`; `savePhotosFromText` in `lib/photos.js`, type sniffed from the bytes: JPEG/PNG/GIF/WebP up to 5 MB; anything else, or a link voip.ms won't serve, stays only as the link and is logged as a warning), `source = 'sms'`, waiting for permission. Once the signup is finished the bot texts `photo_ask` (share publicly incl. social media? everyone in it, or a parent, must agree; YES or NO): with the first picture of a batch (not again while photos are waiting), or right after finishing when pictures came during the signup. A YES/NO (`engine.yesNo`, in their language or English) in phase `done` while photos wait answers for all of them: YES sets `consent_at` and `consent_text` (the question and their reply), NO sets `declined_at` (kept, "Not for sharing" in /admin); the reply is `photo_yes` / `photo_no` with their page link (`#photos`). Any other YES goes to the team as before. Each texted photo after signup gets a receipt: `photo_received` linking to `/p/<key>#photo-<id>` (the page opens that photo large), or `photos_received` linking to `#photos` for several in one text. The Photos tab and the single-photo view say photos are shown for a limited time (`web_photos_temporary`). /admin labels texted photos "By text" and "Awaiting permission" / "Not for sharing". Not yet: sending pictures from /admin (open question 4).

## Decisions (the user's; details in docs/session-2026-10-23.md)
- Any text starts or continues a signup; no keyword.
- No numbered summary to confirm: the last answer finishes the signup, and changes are made on the pastor's page (link in the thank-you). Churches outside the US are accepted (country question; free-form region and postal code).
- One church per phone number. Multi-church was proposed and declined. Known risk: RESTART after DONE wipes that phone's answers.
- Every prompt at most 160 characters. Long translations are fixed by shortening the English and translating again.
- Reviewers share the signup number. A finished signup's free text goes to the team thread; there's no open/close chat switch. Alerts: unread badges only.
- All users have equal rights. Editing answers never changes the texts.
- Simulations live in the real database, flagged and badged, and are never texted.
- The public map exists elsewhere; this app only stores `public_map`.
- Workflow: work on `claude/intelligent-brown-8znoxb` reset onto `main`, then a PR, merged only when the user says so. Migrations are applied through the Supabase MCP and also saved under `supabase/migrations/`.

## Tooling quirks
- Supabase returns at most 1000 rows per request. `btw_prompts` (one row per prompt per language) passed that with the country change (1053 rows) and was 1203 on 2026-10-24, so the newest prompts silently went missing (a texted photo's permission question went out empty: voip.ms `message_empty`). Whole-table reads use `dbAll()` in `lib/supabase.js` (pages with `limit`/`offset`; give it an `order`), and an empty reply is logged instead of sent.
- Supabase MCP: reads and `apply_migration` work; DELETE via `execute_sql` times out (use `/admin`'s Delete button).
- Vercel MCP: deployments and runtime logs work (project `prj_0mYe7r3u736ewePhPOnodWuQQSQ7`, team `team_lgFLmF4DFBT7H0DS0A1KcLNr`); listing env vars is forbidden.
- The live site isn't reachable from the sandbox; test with `dev/server.mjs` and Playwright (`/opt/pw-browsers/chromium`).

## Open questions (verify against https://voip.ms/m/apidocs.php)
1. ~~Format of the incoming callback~~: answered live. voip.ms sends GET with the placeholders filled in and `&` between them, e.g. `{"id":"113367333","from":"9498709493","to":"7147165116","message":"Hi 2","date":"2026-10-23 11:37:00"}` once normalized (`date` is local time, no zone). `flattenBody` / `parseQuery` could be simplified to match. One request took about 7 seconds end to end (incl. a relay send).
2. Does `rest.php` accept POST for `sendSMS`, or only GET? The code POSTs form-encoded data for both.
3. The response field holding the message id: `sms` for `sendSMS`, `mms` for `sendMMS`? The code assumes so.
4. Does `sendMMS` accept media URLs in `media1..3`, or only base64? (Needed before reviewers can send pictures.)
6. How long do the `{MEDIA}` links stay up, and do they need a login? Check with a real MMS: if the thumbnail in /admin doesn't load, the links aren't public.
5. ~~Placeholder names~~: `{TO}`, `{FROM}`, `{MESSAGE}`, `{ID}`, `{TIMESTAMP}` all fill in.
